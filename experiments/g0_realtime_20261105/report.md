# G0 实时性能独立实验（2026-11-05）

**两段完整视频上，组合优化将核心处理速度从3.38fps提高到8.28fps，约2.45倍。
全部2694帧的S2/G0最终掩膜零像素变化；30fps仍未达到。**

本实验只在 `experiments/g0_realtime_20261105/` 和
`runs/g0_realtime_20261105/` 新增文件。`final/` 完全排除，未读取、修改或运行其中内容。
原仓库算法、配置、模型、数据及默认入口保持原样。

## 测量对象与结论边界

测量当前实际链路：原始视频解码 → Raw2 双网 → 顺序 S2 → 最新无回退 G0。
模型为旧190结石网和 A0 model1 光纤网，FP32、batch 1、PIL 256 输入、原生400像素输出。
不是用缓存冒充实时网络前向，也没有跳帧、改阈值、减小分辨率或取消 S2。

`core_ms` 包括预处理、两个网络、必要的原图概率/掩膜传输、S2 和 G0；
GPU 在计时边界同步。`decode_core_ms` 再包括视频读取。
审计哈希、逐帧日志和 PNG 保存不计入上述两项，另报含导出的吞吐。
本实验不运行显示窗口或高分辨率评审视频编码，因此不声称已验证摄像头采集到显示的总延迟。

每个方案、每段视频一个新进程；四个进程顺序运行，没有互相抢占 GPU。
每进程预热12次后重置 S2/G0 状态。所有帧顺序处理并使用已有源时间戳。
对照结果始终是当前无回退 G0，未将旧回退 G0 的精度或成本混入。

|video_1|722|3.337|7.635|2.288×|412.706|174.385|
|video_2|1972|3.403|8.547|2.512×|422.077|147.085|

## 距离30fps还缺什么

优化后2694/2694帧的核心耗时仍超过33.33ms，未通过30fps预算。
S2+G0平均仍分别约93.91ms和80.21ms；即使假设双网耗时为0，
按当前串行CPU工作量也只有约10.65/12.47fps的上界。
因此仅换小网络、FP16或视频编码器不足以实现目标。

下一步优先顺序：

1. 在保持像素判据和状态更新的前提下，继续融合S2颜色/梯度/掩膜运算，减少整图扫描和临时数组；
   尝试编译CPU算子或GPU上的批量融合，并把上传、回传与同步计入成本。
2. 将无历史依赖的下一帧神经推理与本帧CPU后处理做有界流水重叠，限制队列长度，
   分开验证吞吐、单帧延迟和历史顺序，不能用丢帧或队列积压制造fps。
3. 再单独验证网络推理的编译/低精度路径。低精度可能改变高置信种子、类别竞争和尖端，
   需要新的完整等价性或明确的精度验收，不能默认沿用本次零像素变化结论。

现有评审视频还包含1920×820的三栏高质量缩放、PIL绘字和同步管道式libx264 medium编码。
这些适合离线审阅，实际实时界面应另测轻量显示与异步导出；但它们不在上述核心耗时中，
省略它们不会消除已测得的S2/G0计算瓶颈。

## 已确认的瓶颈

初始 CPU profile 显示，S2 为几何条件已失败的端帽候选继续执行整图椭圆栅格化、
边界距离变换、RGB采样和实际边界匹配。S2 的方向估计还调用通用侧边修整接口，
而它只使用返回的方向模型与上下文，丢弃了另外四个返回值。

G0 和 S2 有大量400×400临时数组、重复颜色评价和逐 bin 扫描；
模型计算不是整个流程的最大耗时。原环境同时配置 Torch 16、OpenCV 24、OpenBLAS 24 个线程，
本实验在优化进程内将其限制为1，避免小数组工作使用过多线程。
这只是该进程的设置，没有修改系统或环境配置。

## 优化实现

1. **按原优先级延迟计算端帽。** 先保留原侧边求解、RMS和切线判据，
   按原 `(score, RMS, r)` 稳定顺序检查候选，第一个合格者就是原算法选中的候选。
   对较差候选不再计算已无机会改变输出的整图栅格与显示诊断。
2. **仅计算方向真正使用的返回值。** 保留原 profiles、权重、鲁棒模型和方向规则，
   省略该调用中被丢弃的颜色证据、侧边修整掩膜和保留率诊断。
   上游仅供显示的 `ConnectedBlue.end` 诊断省略，S2自身的真实终止/端帽判据仍执行。
3. **颜色必要条件提前筛除。** 先用原蓝色优势和噪声必要条件排除不可能通过的像素，
   对剩余像素执行原连续评分和距离计算。小范围端部/曲线采样仍使用全部原连续分数，
   包括非蓝色背景分数，避免改变终止判据。
4. **减少 G0 栅格工作。** 稳定分组侧边采样，保留原顺序、极值及均值；
   缓存像素坐标，在保守包围框内执行原双精度半平面与圆判定，输出仍为完整原图掩膜。
5. **控制线程数量。** 优化进程使用单线程库设置，与上述优化一起进行全片验证。

所有权重、原始概率、形状公式、拟合区间、候选阈值、最远蓝色尖端规则、
G0无回退策略和Raw2结石保护均保持原定义。

优化版是最终掩膜/几何运行路径，**不替代完整实验诊断接口**。
它有意不生成所有被拒候选的审核图层；全图连续 evidence score 中不可能通过必要条件的部分
不再计算。掩膜、是否可构造、尖端源像素、T、轴、侧线、圆心、半径和结石裁切量均单独对照。

## 产物与复现

代码入口：

- `fast_stage2.py`：方向专用接口、原排序端帽延迟评价。
- `fast_evidence.py`：必要条件预筛；小范围连续评分保留。
- `fast_geometry.py`：稳定分组、坐标缓存、保守栅格区域。
- `benchmark.py`：独立进程、完整分段计时、身份与输出保存。
- `compare.py`：重新读取所有PNG，检查像素、概率哈希与几何。
- `test_equivalence.py`：针对变化部分的差分测试。

已有 `uretersam` 环境；实验额外使用其中已安装的 `threadpoolctl`，没有安装或升级依赖。
在仓库根目录运行（输出根目录必须不存在）：

```powershell
& ./experiments/g0_realtime_20261105/run_full.ps1 -OutputRoot runs/g0_realtime_new
```

运行单个优化视频：

```powershell
& 'E:/Apps/Conda/miniconda3/envs/uretersam/python.exe' -B -m experiments.g0_realtime_20261105.benchmark --variant fast-runtime --video video_2 --output runs/g0_realtime_video2_new
```

`--diagnostic` 只选择预先列出的重点帧，历史更新也只发生在这些帧，
因此它是机制/性能预检，不能代替完整因果回放。`--profile` 会增加测量开销，
其结果仅用于定位瓶颈，正式性能比较不启用 profiler。

每个完整运行保存源码/配置/权重/视频身份、环境、逐帧耗时、G0几何、原图S2和G0掩膜。
逐帧原始RGB和原S2掩膜还与已有历史哈希对照。运行前后检查网络状态与源码身份不变。
