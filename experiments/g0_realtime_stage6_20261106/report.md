# G0 恢复 v4 与第六轮 NumPy 优化实验

2026-11-06。**已取消 Windows x64 DLL 优化，恢复 v4 NumPy 基线。** 新的纯 NumPy S2 坐标域候选同轮合并吞吐 **10.56 → 11.41 FPS（+8.07%）**，CPU 后处理 **59.58 → 54.62 ms/帧（−8.32%）**；2,694 帧 S2/G0 掩膜零像素变化，56 项检查通过。仍未达到 30 FPS。

`final/` 全程不读取、不运行、不修改；原工具、模型、配置及前四轮实验不修改。v4 回退入口继续保留，新候选只放在本轮独立实验中。

## 已完成的恢复

v5 的 `runtime.Runtime` 已变为 v4 NumPy `Runtime` 的直接别名；旧命令中的 `v5-serial` 明确转到 v4，并记录真实的 `v4-serial` 身份。自定义原生模块的实例化、构建、微基准及旧版完整测量入口已停用。

旧 DLL、C++ 文件和测量产物只作历史记录，未删除，也不会参与当前运行。撤回前源码单独存入 `runs/g0_realtime_stage6_20261106/withdrawn_v5_sources.zip`。撤回前后哈希见 `rollback_before.json` / `rollback_after.json`；前四轮的 208 个源码/配置文件仍与历史一致。

回退检查验证运行类与 v4 是同一对象，禁止自定义 DLL 加载时仍能初始化和处理测试场景，旧命令的两种参数形式都转为 v4。旧入口另外重放 23 个重点帧，与历史 v4 的掩膜、概率、决策和几何比较通过。

## 新候选的范围

第六轮仅改变 S2 的候选坐标域计算与前向边界检查，继续使用 v4 的 NumPy/OpenCV/PyTorch 环境：

- 先按原行序提取身体像素，用原逐点运算和精确分位数得到轴向、侧向范围。
- 对范围求保守矩形，使用实际轴/法向矩阵的逆，再加 2 像素保护；不能可靠计算时退到全图。
- 用绝对整数行、列的一维 NumPy 广播计算框内投影，保留逐点的乘加顺序；既减少计算域，也减少重复二维临时数组。
- 前向边界检查只投影恢复后的实际像素，保持原比较规则。

完整 RGB 证据图、完整梯度、域外身体像素和全部连通传播图保留。端帽拟合、G0、网络模型、精度、每帧两次前向、阈值和时序规则均沿用 v4。没有新增编译模块、SDK 或包；原有 NumPy/OpenCV/PyTorch 的标准二进制依赖不变。

## 预检

当前检查共 56 项，通过后才启动正式测量。新增用例逐值检查 240 组不同方向、比例和原点的完整候选域，并覆盖精确边界、图像边缘、空框、病态矩阵及状态序列。状态序列包括断裂、结石、无目标、面积预算回退、恢复与重置，比较中间域、最终 S2/G0、端帽信息及原输入不变性；另验证审计位打包的精确重建、非整字节边界和非法标签拒绝。

候选另外通过 23 个重点帧与恢复后 v4 的精确输出对比。该筛选不是完整视频准确率评估。

候选域单项微基准，5 次预热、40 次交替顺序配对，单线程 CPU 库：

| 场景 | v4 完整坐标网格 ms | NumPy ROI + 广播 ms | 局部倍数 |
| --- | ---: | ---: | ---: |
| 固定身体，框占图像 21.44% | 4.4186 | 0.6768 | 6.53 |
| 分散身体，框为整图 | 4.5652 | 1.9807 | 2.30 |

后者说明收益不只来自裁剪，广播本身也能减少中间数组；但这两组场景不是完整视频消融，不能精确分解真实流程中两项各自的贡献，更不能把局部倍数当成 FPS 增益。

## 完整测量设计

同轮 v4-serial 与 v6-serial，video_1 共 722 帧、video_2 共 1,972 帧。每案例独立进程，12 次预热后重置，单线程 CPU 库；video_1 顺序 v4→v6，video_2 顺序 v6→v4。

FPS 为合并总帧数除以合并墙钟，包含解码、同步网络、CPU 后处理、轻量审计、掩膜内存复制及无损位打包，批量 PNG/日志导出在计时外。后处理和单帧结果延迟在审计打包前结束计时，与之前的计时边界一致。延迟从帧进入处理到结果完成；不含摄像头采集、显示、编码或进入处理前排队。只验证串行，不能宣称已有 v6 流水线结果。

要求原视频和检查点身份一致、网络概率与 Raw2 哈希一致、S2/G0 逐像素一致、G0 决策一致且几何满足 1e-9 比较容差，检查历史 S2、结石保护、前向次数、帧顺序、模型与源码不变性。归档不包含自定义 DLL，身份中明确记录 `custom_g0_dll_enabled=false`。

每视频每方案一次完整运行；帧级 P95 不能作为重复实验的置信区间。环境负载和频率可能变化，不能用上一轮不同条件的绝对 FPS 推断新候选的加速。

首轮尝试保留在 `runs/g0_realtime_stage6_20261106/full/`：video_1 两组均完成且输出一致，video_2 两组在推理开始前因可用内存不足触发保护，故该轮不能计算两视频合并结论。没有降低保护阈值或中断其他程序。随后仅将审计缓存从 uint8 原图改为无损二位标签存储，完整两视频对照全部重新运行，保存在 **`full_packed/`**；同轮两方案采用相同审计方式。video_2 缓存从约 631 MB 降为约 158 MB，解包后继续独立读取 PNG 比较。该改动只用于实验记录，不进入分割算法。

四组共执行 5,388 个正式帧、48 个预热帧。四项完整比较全部通过：同轮两个 v4/候选比较，以及两个 v4/历史 v4 比较。解包并重新读取 PNG 后，S2/G0 改变像素均为 0；Raw2、网络概率、帧身份、G0 决策和几何均满足原合同。每方案 G0 应用 2,654 帧，原有不可用 40 帧及原因相同，S2 端帽接受共 1,372 帧，结石标签零变化。

225 个纳入本轮清单的源码/配置/脚本与四份归档一致，其中原有 208 个文件仍与第四轮身份相同。模型状态不变。四份源码归档 SHA256 相同：`acb63eab467ff546724242b438d0fd2a33613f9dfb985a3a25a827d1316092bf`；不含自定义 DLL 或 C++ 模块。机器可读结果为本目录 `results.json` 和 `runs/g0_realtime_stage6_20261106/full_packed/result_summary.json`。

## 剩余热点与后续优先级

正式视频中，S2 仍占 CPU 后处理 **84.33%**。完整实验之后对相同 23 个重点帧重新采集 CPU 剖析，且重放与历史 v4 仍零像素差异。含剖析开销，平均约 66.5 ms/帧，以下累计值相互包含，不能相加：

| 热点 | 每剖析帧累计 ms | 说明 |
| --- | ---: | --- |
| S2 expand | 22.88 | 包含梯度、证据、端帽 |
| 初始蓝色生长 grow | 17.38 | 包含种子识别及颜色/连通处理 |
| S2 fit_cap | 10.06 | 17 次调用摊入 23 帧 |
| 分组剖面 | 4.43 | 两条父路径共 40 次调用 |
| 完整梯度 | 3.57 | 保留原图真实邻域 |
| 端帽共享准备 | 3.05 | 12 次调用摊入 23 帧 |
| 新坐标域构建 | **0.88** | 已不是主要热点 |

下一步仍坚持 NumPy 路径，优先做：

1. **复用当前帧色度，减少初始生长中的重复归一化。** `grow` 当前先取 `frame[region]`，随后颜色判断又计算色度；后面的 S2 还需整帧色度。可将已缓存的整帧色度/噪声按同一 region 行序取出，直接送入原颜色公式，保持 float32 三通道求和顺序和全部小探针回退规则。这一改动尚未实现，要逐值验证颜色判据，并检查无有效 S2、弱历史等分支的开销，不能预先承诺倍数。
2. **将一维广播推广到 grow 和端帽的坐标准备。** 这些路径仍保留二维网格上的多遍减法/乘法；只替换坐标构造与临时数组，先不裁剪连通域、端帽外围或距离变换。单独消融“广播”“色度复用”，再做组合全量对照，避免混淆贡献。
3. **之后验证纯 NumPy 新版的有界流水线。** 当前没有 v6 流水线实测；已有旧版流水数据不能直接套用。继续同时测同轮 v4 基线、帧延迟及 CPU/GPU 争用。

全部 `lstsq` 在该剖析中约 1.5 ms/帧，因此不优先改写小求解器，也不通过减少拟合、近似分位数或跳帧换速度。

以本轮 CPU 后处理 54.62 ms/帧估算，即使网络完全重叠且无额外争用，CPU 阶段也只允许约 **18.31 FPS**；这不是已测流水结果，帧延迟也不会变成两个阶段耗时的最大值。要达到 30 FPS，CPU 后处理至少还需下降约 **38.97%** 到 33.33 ms 以下，并为其他工作和波动留余量。网络 P95 也超过 33.33 ms，不能只靠本轮局部改动承诺实时目标。

本轮建议保留该纯 NumPy 候选继续实验；**当前恢复入口仍直接使用 v4**。不重新引入已撤回的自定义 DLL。
