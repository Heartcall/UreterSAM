# G0 第八轮：v7 有界流水线验证

**结论：两帧有界流水将同轮合并吞吐从 12.6534 提高到 18.6490 FPS（+47.3832%），但平均单帧延迟从 78.5943 增至 106.3831 ms。** 两段完整视频共 2,694 帧的 S2/G0 掩膜逐像素一致。它是已验证的吞吐优化候选；当前结果不支持“单帧响应更快”或“已达到 30 FPS”。下一步优先减少 CPU 后处理，而不是增加排队深度。

2026-11-06。两组均直接使用已验证的 v7 NumPy Runtime；本轮仅改变调度并增加时序记录。前七轮代码及恢复后的 v4 入口保持原样。`final/` 全程不读取、不运行、不修改；不启用自定义 DLL、不安装依赖。

## 本轮行为与输出合同

单个工作线程负责解码和原来的同步双网络推理，主线程按原视频帧序、原时间戳执行全部 S2/G0。最多允许两帧同时进入处理：包括正在解码、推理、后处理或等待的帧。额度耗尽时等待，既不丢帧，也不累积无界队列。

S2/G0 仍串行更新状态；帧的 RGB、Raw2、网络概率和当前帧色度缓存不跨帧混用。模型、FP32、输入、阈值、精确分位数、拟合轮数、完整梯度/连通传播和 G0 规则均不改。单独的 runtime.py 直接导入原 v7 类，没有新分割实现。

## 检查与测量方法

64 项检查通过，含原 60 项及新增时序分析检查。新增检查覆盖单阶段不自相重叠、帧序唯一、时间顺序、有限数、在途上限和已知区间的重叠计算。另用 23 个重点帧实际运行串行与流水并重读 PNG，S2/G0、概率、决策与几何一致；串行也与历史 v7 对照通过。流水在途峰值为 2，出现了真实的网络服务/后处理重叠。

完整对照每视频每方案一次，video_1 共 722 帧、video_2 共 1,972 帧，各自独立进程，12 次预热后重置状态，CPU 库单线程。video_1 先串行后流水，video_2 反序。每帧各运行一次结石和光纤网络，原视频时间戳直接传入后处理。

FPS 按合并总帧数 / 合并总墙钟计算，包含解码、同步推理、CPU 后处理、轻量时序/哈希记录及无损审计位打包；批量 PNG/日志导出在计时外。单帧延迟从获准进入处理/开始解码到后处理结果完成，不计审计打包和进入处理之前的等待，也不计启动、摄像头、显示及编码。它是离线文件重放指标，不能当成完整摄像头到显示延迟。

本轮逐帧记录网络服务与后处理的主机 perf_counter 区间、释放时刻、原时间戳及执行线程。重新检查这些记录来验证在途上限和顺序，并计算两个服务区间的交集。网络服务含原预处理、传输与同步等待；交集不是纯 GPU 内核占用率。原 CUDA 事件仍用于两个模型实际 forward 计时。

串行原调试计数在解码成功后增加；新时序从取得额度、准备解码开始记录，所以时序峰值包含解码期保留的额度。两者分别检查且均不能越过 1 / 2 帧的配置上限。

## 内存保护记录

首次小规模启动在模型构建及正式计时前因可用内存不足退出。单独探测显示，导入前约 1.75 GB 可用，导入既有依赖后约 488 MB（465 MiB），不足原保护余量。没有降低阈值，也没有终止其他程序。用户释放内存后重新启动，保留原阈值及原有无损审计格式，完成小规模验证后才开始完整对照。失败日志和 memory_probe.json 均留存。

## 完整结果

| 同轮合并指标 | v7 串行 | 同一 v7 两帧流水 |
|---|---:|---:|
| 输出吞吐 / FPS | 12.6534 | 18.6490 |
| 总墙钟 / s | 212.9070 | 144.4582 |
| 单帧进入处理至结果平均 / ms | 78.5943 | 106.3831 |
| 单帧进入处理至结果 P95 / ms | 103.0219 | 128.6960 |
| 已完成推理后等待后处理平均 / ms | 0.0023 | 24.9696 |
| 网络完整服务平均 / ms | 26.1076 | 25.9503 |
| S2 平均 / ms | 41.4320 | 44.9057 |
| G0 平均 / ms | 8.6088 | 7.9545 |
| CPU 后处理完整服务平均 / ms | 50.3374 | 53.1578 |
| 已进入处理的在途帧峰值 | 1 | 2 |

完整处理节省 68.4489 s；平均单帧延迟增加 27.7889 ms，P95 增加 25.6741 ms。后处理完整服务包括少量 Runtime 包装开销，略大于 S2 与 G0 之和。流水并未缩短每帧总服务时间；CPU 后处理平均反而增加 5.60%。这种差异与并发资源竞争相容，但每方案每视频只测一次，不能把差异完全归因于竞争或某个具体函数。

| 视频 | 帧数 | 串行 FPS | 流水 FPS | 吞吐变化 |
|---|---:|---:|---:|---:|
| video_1 | 722 | 13.8191 | 20.8342 | +50.76% |
| video_2 | 1,972 | 12.2743 | 17.9593 | +46.32% |

逐帧主机服务区间显示，流水网络服务共 69.9102 s，其中 69.8146 s 与 CPU 后处理交叠：网络服务重叠比例为 99.8632%，后处理重叠比例为 48.7507%。网络与后处理分别在一个不同线程上执行，各自严格串行，后处理沿用原始帧序和视频时间戳。这里的 99.8632% 是同步网络服务区间的覆盖比例，不能解释为 GPU 利用率。

以本轮流水后处理平均 53.1578 ms 估算，即使其他服务完全隐藏，单后处理线程的容量也约为 18.8119 FPS；实际吞吐已达到这一估算值的 99.13%。因此增加第三帧缓冲预计只能消除很少的空隙，同时会增加帧等待；本轮没有测量三帧模式，此判断是基于已测时序的推断。

四项完整独立比较全部通过：每个视频流水对本轮串行，以及本轮串行对上一轮完整 v7。重新读取 PNG 后，S2/G0 改变像素和改变帧均为零；输入 RGB、Raw2、光纤概率哈希一致，G0 决策和几何在绝对容差 1e-9 内一致。各案例还核验历史 S2、结石像素、模型状态、完整帧数与每帧两个网络各一次 forward。每方案 G0 应用 2,654 帧，40 帧按原规则不可用；S2 接受端帽 1,372 帧。所有优化、区域及空间计数在串行/流水间完全相同。

正式共执行 5,388 帧，另有 48 次预热；四个进程的源码归档 SHA256 完全一致。239 个源文件/配置与归档和当前文件逐项一致，上一轮冻结的 233 个文件未变；自定义 G0 DLL 状态为关闭。

每视频每方案只测一次，帧级 P95 不是重复实验的置信区间；其他轮次不同负载下的绝对 FPS 不作累计加速依据。以上延迟不含进入处理前的等待。对于持续 30 FPS 的相机输入，当前能力还不足以无等待地处理所有帧，摄像头或上游可能继续积压，不能用两帧在途上限证明完整采集到显示延迟有界。

## 剩余瓶颈与下一步

完整计时结束后，另用 23 个重点帧在相同流水调度下只剖析主线程后处理；先预热 12 次并重置状态。剖析重放与上一轮同组帧的 S2/G0、输入、光纤概率和几何比较通过。剖析开销使后处理平均达到 74.1156 ms，以下仅用于定位，不能替代上表性能；嵌套累计耗时不能相加。

| 剖析入口 | 每测量帧累计平均 / ms | 说明 |
|---|---:|---|
| S2 整体 | 61.4628 | 主要 CPU 路径 |
| RGB 连通生长 grow | 20.8009 | 含种子、颜色门限、连通和数组扫描 |
| S2 expand | 21.4295 | 含证据、完整图传播和 fit_cap |
| S2 fit_cap | 9.4700 | 17 次调用总计 / 23 帧；每调用 12.8124 ms |
| 种子资格 seeds | 8.2752 | 已有帧内种子复用，剩余内部组件处理 |
| region_color | 6.7068 | 含首次色度计算和区域提取 |
| G0 整体 | 12.3528 | 含几何、侧线及尖端 |
| grouped_profiles | 5.3789 | 40 次调用总计 / 23 帧 |

代码核验后的候选优先级：

1. **减少生长/区域颜色路径中的数组提取与重复扫描。** grow 仍在完整网格上生成 t、normal、domain，region_color 又扫描 region 并分别提取 color/noise；种子核心也独立提取坐标。下一轮可在帧内复用同一非零索引/包围框，将区域颜色计算限制到精确同一像素集。必须保留绝对坐标、运算顺序、行优先索引和边界语义；连通图不能直接截断。先测固定输入的 isolated kernel，再比较整体流水，不能只看局部速度。
2. **种子组件的扫描与拷贝复用。** QualifiedSeedObserver 先做 4 连通组件，再为每个候选复制 isolated mask，调用父类完整种子逻辑。可以研究复用同一候选的坐标、组件统计和掩膜构建；保留连通性、面积门限、候选排序、歧义和 prior/age 语义，不引入跨帧旧种子。收益需实测，当前 8.2752 ms 是带剖析开销的定位值。
3. **同一几何上下文内复用 profile 与采样索引。** grouped_profiles 和 sample 仍被多处调用。仅当输入掩膜、坐标系、步长、边界规则完全相同时才共享；不同阶段的恢复掩膜和不同轴不能复用。fit_cap 的 12 次稳健拟合、精确分位数、候选排序仍保留，不用减少迭代次数换取未经验证的几何变化。

若目标为 30 FPS，仅后处理平均就需从 53.1578 降至 33.3333 ms 以下，即至少减少约 37.29%，并留出解码、记录和未隐藏推理的余量。这是容量要求，不是对下一轮收益的承诺。当前网络服务平均约 25.95 ms，只有当 CPU 明显缩短后，才需要重新判断网络是否成为瓶颈。吞吐候选与串行低延迟候选均保留为独立入口，本轮未更改正式部署入口。
