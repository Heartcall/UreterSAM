# G0 第二轮实时优化实验

日期：2026-11-05。范围：仓库内独立实验；`final/` 未读取、未运行、未修改。第一轮实验和原有模型、配置、工具代码保持冻结。

## 结论与全量结果

**第二轮已完成：本轮串行版综合 9.10 FPS，流水版 13.68 FPS；两者在全部 2694 帧上保持 S2/G0 掩膜零像素变化，仍未达到 30 FPS。** 相比同一测量入口中的第一轮优化版，串行吞吐提升 15.8%，流水吞吐提升 74.2%。

| 方案 | 视频 1 FPS | 视频 2 FPS | 综合 FPS | 平均接纳至结果延迟 ms | P95 延迟 ms |
|---|---:|---:|---:|---:|---:|
| 第一轮版串行 v1 | 8.37 | 7.68 | 7.85 | 127.08 | 164.64 |
| 本轮版串行 v2 | 9.41 | 8.99 | **9.10** | **109.70** | **134.56** |
| 本轮版流水 v2 | **13.51** | **13.74** | **13.68** | 145.52 | 168.79 |

综合 FPS 为总帧数除以两视频测量总时间，P95 由合并后的逐帧记录计算，均非各视频数值的简单平均。

**使用建议：交互优先选择 v2 串行；连续文件处理且吞吐优先选择 v2 流水。** 流水相对新版串行再提高吞吐 50.4%，但平均延迟增加 35.82 ms、P95 增加 34.23 ms，平均排队 37.86 ms。没有更改原工程默认入口。

本轮串行 CPU 后处理下降 **22.4%**，G0 阶段下降约 **43.3%**。网络仍运行同一原函数，并未出现本轮串行网络加速；不同阶段的实际时间受主机调度和频率影响，应以完整路径结果判断收益。

全量计数显示，尖端前向证据检查由 7,617,633 个候选减少为 119,925 个，减少 **98.43%**；这只指昂贵的后续证据检查，候选域生成和排序仍然执行。主体结果复用 2694 次，同帧证据复用 1439 次，色度缓存命中 2689 次。两视频未触发弱历史复用禁用分支，该分支另有专项测试覆盖。

六组共处理 8082 帧，两网络各实际前向 8082 次，另有 72 次预热双网络调用。六项独立全量比较全部通过：Raw2、光纤概率哈希一致；S2/G0 重读 PNG 的改变像素均为 0；记录的 G0 决策和几何满足合同；2654 帧正常重建、40 帧不可用的分布完全相同（35 帧尖端达到/超过交点、2 帧无可信主体、3 帧主体歧义）。所有方案均保留 1372 次 S2 cap 接受结果，结石像素不变。

40 项测试通过，运行前后模型状态与 196 个源码/配置文件身份不变。六组保存相同源文件清单和可追溯归档；第一轮原结果也与本轮 v1 完整核对通过。机器可读汇总见本目录 `results.json`，原始证据见 `runs/g0_realtime_stage2_20261105/full/`。

## 本轮改动与适用条件

实现位于 `runtime.py`，新增公共测量入口 `benchmark.py`，不替换原工程默认入口。

1. **同帧复用主体识别**：S2 与 G0 的识别配置相同，同一图像、Raw2、概率对象且主体不依赖历史弱证据时，G0 复用 S2 结果。有 `weak_history` 或输入对象不一致时重新计算，禁止跨帧复用。
2. **同帧复用色度及证据**：只缓存当前完整图像的色度；证据复用还要求梯度对象、配置、主体颜色参数完全一致。每帧、状态重置时清空缓存。
3. **尖端按原优先级惰性求证**：先保留原来的候选域、局部蓝色像素门槛和结石排除，再按原来的轴向/法向排序依次检查。找到首个合格候选即停止；无合格点则检查完整候选集。判据、排序与最终选择不变。
4. **减少分组和诊断开销**：轴向截面稳定分组，保留每组原像素顺序及计算结果；省去不参与掩膜决策的全图诊断计数、图层和 Lab 转换。惰性搜索的完整合格点数设为 `None`，显示图层只含已检查点。因此，本实验承诺最终掩膜与决策等价，不能替代原版完整诊断导出。
5. **有界流水处理**：一个工作线程顺序解码及推理，主线程按原帧顺序运行有状态 S2/G0。最多同时接纳两帧，即当前帧加提前一帧；不跳帧、不并行修改后处理状态。

## 为什么优先处理这些位置

第一轮优化后的 23 个重点帧 CPU 剖析表明，仍有两次主体识别、全图颜色/证据重复生成和大量最终不会被选中的尖端候选检查。该剖析中，S2 `expand` 累计约 41 ms/帧、连接蓝色区域 `grow` 约 21 ms/帧、G0 `locate_tip` 约 16 ms/帧，两次 `seeds` 合计约 13 ms/帧。这些是**嵌套累计时间，不能相加**，且包含剖析开销；仅用于定位，不作为性能结论。

记录：`runs/g0_realtime_stage2_20261105/profile_current/cpu_profile.txt`。

全量完成后，另对新版采集了 CPU 剖析，保存在 `profile_v2/cpu_profile.txt` 和 `hotspots.json`。这次采样包含 12 次预热及 23 个重点帧，共 35 次后处理调用，**不与前一份剖析直接计算加速比**。新版 `expand` 约 37.3 ms/调用、`grow` 25.1 ms/调用、`native_gradient` 7.8 ms/调用，仍是应优先处理的路径；`grow` 包含主体识别，`expand` 包含梯度等子调用，这些数值同样不能相加。剖析回放的 23 帧另行通过精确输出比较。

## 对照与计时范围

三组预先固定：第一轮优化版串行 `v1-serial`、本轮版串行 `v2-serial`、本轮版流水 `v2-pipeline`。每组完整运行两段视频（722/1972 帧），每组使用独立进程；模型仍为原双网络、FP32、batch=1、256 输入，原始图像 400×400。实际推理线程预热 12 次，随后重置后处理状态与计数。CPU/OpenCV/BLAS 线程均限制为 1。所有运行依次执行，避免实验之间争用 GPU。

本轮 FPS 为**实际完成帧数 / 测量墙钟时间**，包含顺序视频解码、同步网络推理、后处理、队列、轻量哈希和内存掩膜副本。PNG 和日志文件在计时结束后统一导出。用于审计的两张 uint8 掩膜缓冲占视频 1 约 220 MiB、视频 2 约 602 MiB；启动前检查主存余量。该缓冲是实验审计设施，实际运行不必累计保存全部掩膜。

单帧延迟定义为**获得接纳名额、开始解码至后处理结果可用**。流水延迟包含入队后的等待，但不包含获得接纳名额之前的背压等待。这里没有接入实时摄像头，也不计显示、视频编码或从视频 PTS 起算的等待，不能称为摄像头到显示延迟；若实时输入不允许跳帧且输入速率持续大于处理速率，等待仍会累积。

`network_ms` 包含网络输入准备、两次前向和结果回传；CUDA Event 另测两次顶层前向区间。GPU 异步计时必须处理同步，方法依据安装版本 [PyTorch 2.11 CUDA 文档](https://docs.pytorch.org/docs/2.11/notes/cuda.html#asynchronous-execution)。CUDA Event 区间也可能受调度影响，不能单独据此断定纯计算瓶颈。

第一轮报告的 FPS 使用各帧核心服务耗时之和作分母。本轮统一加入解码/审计等实际墙钟开销，**不同计时口径不能直接计算跨轮加速比**；本轮三组之间可以比较。每视频每方案执行一次全量，帧级 P95 是观测分布，不是重复试验的置信区间。系统负载、频率等仍会影响数值。

## 验收与复现

- 完整两段视频逐帧比较 Raw2 和光纤概率哈希、S2/G0 掩膜；独立重读 PNG 统计改变的像素。
- G0 可用状态、原因、尖端来源相同，所记录几何量绝对误差不超过 1e-9；结石像素不能改变。
- S2 另与原工程历史每帧哈希核对；本轮 v1 另与第一轮完整结果核对。
- 检查输入视频/模型 SHA256、模型运行前后状态、原有及实验源文件哈希、两网络实际前向次数、帧序及在途上限。
- 专项和原有检查共 40 项；测试日志 `runs/g0_realtime_stage2_20261105/tests.log`。

本轮验收是对现有 G0 行为的保持验证，不是新标注集上的准确率或临床验证。相同像素能够证明这些回放中没有改变 G0 的输出，不能证明未见输入上的普遍等价性；新增弱历史回退、边界和无尖端等专项检查用于补充覆盖。

运行入口：在仓库根目录执行 `experiments/g0_realtime_stage2_20261105/run_full.ps1`。使用现有 `uretersam` 环境，不安装新依赖；已有输出目录会拒绝覆盖，可用 `-OutputRoot` 指定新目录。源文件归档、环境身份、逐帧计时、掩膜和对比结果保存在 `runs/g0_realtime_stage2_20261105/full/`。

## 后续优化的边界与顺序

优先降低 S2 的连接区域扩张、颜色证据及梯度等 CPU 服务时间，再评估固定形状网络的启动开销。流水版 CPU 平均 72.78 ms，对应忽略其他开销时约 **13.74 FPS** 的平均服务能力，已经接近观测到的 13.68 FPS。只优化网络无法消除这一上限；继续扩大队列也不会提高 CPU 的服务能力。

30 FPS 对应每阶段约 33.3 ms 的持续处理预算，单帧低延迟还要求总路径满足预算。仅把当前串行版 CPU 阶段压到这一预算，就需再减少约 **53.7%**，且网络、调度及长尾仍须单独达标。两种新版的全部 2694 帧接纳至结果延迟均超过 33.3 ms，不能宣称已经实现 30 FPS 实时处理。

下一轮按本轮新版剖析，先把 `grow`、`expand` 中的颜色判据、坐标投影及梯度等数组遍历合并到编译函数或一致的 GPU 数据路径，减少临时数组和中间回传。保留原始浮点精度、Sobel 边界、4/8 邻域各自规则、原排序及回退；如缩小计算区域，必须覆盖原连通域及卷积边界所需范围。迁移到 GPU 若每个小算子都往返 CPU，收益未必成立，必须连同传输和同步一起测量。该方向尚未实现，不能给出预期 FPS。

网络可独立探索 FP32 CUDA Graph。安装版本的 [PyTorch 2.11 文档](https://docs.pytorch.org/docs/2.11/notes/cuda.html#cuda-graphs)说明它能减少 Python/C++/驱动的重复启动开销，同时要求静态形状、控制流和稳定地址，并需按文档预热与捕获。本轮没有实现或测得其收益；下一轮仍需重新核对原始概率和完整最终掩膜。

FP16、缩小输入、跳帧、简化结石网络或去掉 S2 会改变数值或算法，不能混入本轮的等价加速结论；如需评估，应单列精度与时序实验。
