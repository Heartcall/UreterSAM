# G0 第九轮：30 FPS 实时输入与 100 ms 延迟目标

2026-11-06。用户明确：输入为实时内镜 30 FPS，采集到叠加显示延迟控制在 100 ms 内。

**结论：当前方案尚未满足这一目标。性能优先级应为：分割与帧对应正确性约束 → 100 ms 端到端期限和帧新鲜度 → 持续有效分割更新率 → 资源占用。** 平均处理 FPS 只作为容量指标。第八轮两帧流水应保留为离线吞吐候选，不能按实时目标直接采用；单独改为取最新帧也不足以达标。

本轮只新增独立实验，`final/` 不读取、不运行、不修改；前八轮、原模型/配置、恢复后的 v4 入口均未变。不启用自定义 DLL、不安装依赖。没有改变实际采集、时序状态或部署行为。

## 验收口径与预算

1. **正确性约束。** RGB、Raw2、光纤概率、S2/G0 掩膜始终带同一个 frame_id 和采集时间；不得把旧掩膜画到最新 RGB。无可信光纤或 G0 不可用时沿用原拒绝规则，不靠旧掩膜补出当前结果。精确计算优化继续要求相同处理序列下逐像素一致。
2. **期限优先。** 延迟从真实采集时刻到结果实际呈现，包括设备缓冲、CPU/GPU、跨线程等待、叠加及呈现；记录 P50/P95/P99、最大值及超过 100 ms 的数量。用户要求是 100 ms 内，P95 小于 100 ms 不能证明全部结果达标。逾期结果可以在拟议实时策略中不呈现，但必须计为超时；不能仅剔除失败帧来宣称达标。
3. **持续有效更新率。** 分别记录采集 30 FPS、实际分割更新 Hz、100 ms 内的不同帧结果 Hz、跳过输入数、废弃推理结果数、最大更新间隔及无有效叠加时长。屏幕刷新 30 FPS 不等于每秒产生 30 个新分割结果。即使每次新结果延迟低于 100 ms，长时间保持旧成对画面也可能使当前屏幕内容过时，需单独监控显示画面的年龄。
4. **资源与稳定性。** 仅在以上指标满足时比较内存/显存和利用率；有界队列、预热、可复现身份与异常退出属于工程要求。

建议作为下一轮实现目标的预算如下，尚未实测或验收：

| 路径 | 拟议耗时预算 |
|---|---:|
| 采集、设备缓冲和取帧 | 10 ms |
| 调度等待及数据交接 | 5 ms |
| 两网络完整推理服务 | 30 ms |
| CPU S2/G0 完整后处理 | 30 ms |
| 叠加与呈现 | 15 ms |
| 合计 / 留给抖动的余量 | 90 ms / 10 ms |

这些是路径预算，不是把各阶段 P95 相加后当作整体 P95。必须直接测同一帧全链路。为持续处理每一个 30 FPS 输入，流水中的每个串行阶段平均服务时间至少需低于 33.333 ms，并保留耗时波动余量；若允许过载跳帧，其结果更新率仍需单独披露。当前未验证的显示刷新率和设备采集延迟会改变预算可行性。一般操作系统下有限视频上的最大值也不是硬实时最坏执行时间保证。

## 已测事实：为何上一轮流水不满足目标

第八轮是完整离线重放，每方案 2,694 帧，保留原始时间戳和全部帧。串行吞吐 12.6534 FPS，进入处理至结果平均 / P95 为 78.5943 / 103.0219 ms；两帧流水吞吐 18.6490 FPS，延迟为 106.3831 / 128.6960 ms。以上均不含进入处理前积压、真实采集或显示。

流水 CPU 后处理平均 / P95 为 53.1578 / 64.5486 ms，网络完整服务平均 / P95 为 25.9503 / 37.9165 ms。网络服务区间已有 99.8632% 与后处理交叠。因而优先减少 CPU 路径，且后续必须压低网络尾部耗时；增大队列无法解决服务能力不足，过载时会延长等待。

若把当前流水 CPU 平均压到 30 ms，需减少约 43.56%。仅降至 33.333 ms 所需的 37.29% 是平均容量下限，不是 100 ms 达标条件。

## 五种实时调度策略的固定耗时模拟

独立模拟器读取第八轮逐帧记录，按 index/30 生成 30 FPS 到达事件。串行策略使用串行轨迹，流水策略使用流水轨迹；服务包含原解码、哈希和审计开销，去除原记录中的已完成推理后等待时间，重新计算等待和帧选择。

| 策略 | 行为 |
|---|---|
| FIFO 串行 | 每帧都处理，未处理的输入继续在上游等待 |
| FIFO 两帧流水 | 内部至多两帧，上游仍保留所有未处理输入 |
| 最新帧串行 | 每次开始处理时选择最新已到达输入 |
| 最新帧两帧流水 | 取得两帧处理额度后选择最新输入，内部仍按序完成 |
| 最新就绪结果流水 | NN 持续处理最新输入；一个可覆盖的 NN 结果槽，后处理每次取最新已完成结果 |

最后一种可能同时有一帧 NN 执行、一帧后处理和一个就绪结果，另有采集最新槽；它与原两帧额度策略不同，不能声称同样在途上限。它可能浪费已完成但未用于后处理的推理工作。所有模拟均不抢占已经开始的计算。

**下表是模拟，不是摄像头实测，也不是实现的加速结果。** 为显示调度本身的限制，采用理想立即呈现、不加入采集/显示额外延迟：

| 视频 / 策略 | 处理帧数 / 输入 | 结果延迟 P95 / ms | 处理结果超 100 ms 比例 |
|---|---:|---:|---:|
| video_1 最新帧串行 | 336 / 722 | 106.22 | 16.37% |
| video_1 最新帧两帧流水 | 508 / 722 | 134.51 | 77.76% |
| video_1 最新就绪结果流水 | 508 / 722 | 123.72 | 23.62% |
| video_2 最新帧串行 | 825 / 1,972 | 124.67 | 37.58% |
| video_2 最新帧两帧流水 | 1,194 / 1,972 | 153.45 | 96.40% |
| video_2 最新就绪结果流水 | 1,191 / 1,972 | 147.09 | 55.84% |

FIFO 两帧流水保留全部输入时，video_1 / video_2 模拟末帧延迟分别约 10.60 / 44.05 s：限制内部队列不能消除上游积压。最新策略控制了积压，但当前计算仍有太多结果超时；最快出结果和最高处理 Hz 并非同一目标下的最优策略。

另做 10 ms 外部预算、60 Hz 呈现的假设敏感性分析。最新就绪结果流水 video_2 的 P95 为 166.67 ms；将所有 CPU 后处理服务假设缩至原来的 60% / 50% / 40% 时，P95 分别为 116.67 / 116.67 / 100.00 ms，但仍有 17.19% / 7.17% / 3.30% 结果超时。它说明仅优化平均 CPU 容量不够，还需抑制尾部与排队；这些缩放比例不是已实现的算法收益。

模拟限制：沿用未跳帧运行时每帧耗时，未预测跳帧后的时序状态、资源竞争、采集抖动或显示阻塞。服务时间随处理序列改变时，这些数字会改变。不能据此批准某一种在线策略，也不能据此声称跳帧后的掩膜与完整运行相同。

## 时序状态核验

实际调用原 EvidenceTracker，构造相同有效初始状态，再输入四次无当前观测。间隔为 1/30 s 时，第 3 次状态仍可预测（经过 100 ms），第 4 次过期（133.33 ms）；间隔改为 0.1 s 时，第 3 次仍可预测（经过 300 ms），第 4 次过期（400 ms）。源码与配置未改。

原因是 prepare 使用真实 dt 预测，update 中 age 每处理一次缺失观测只加 1；现有最大预测次数为 3。种子弱历史门限也以 age<=3 判断。跳帧后必须保留原始采集时间，且需要独立验证以经过时间限制历史有效期的策略；这会改变行为，不能混入精确数值加速。即便当前两段视频中的种子复用已通过，也不能保证新的运动/遮挡序列不受影响。

## 本轮实际 CPU 优化候选

候选保持 v7 全部算法，只把 region 的两次布尔提取改为一次 C 顺序非零索引，并用同一索引获取 color/noise。4096 像素门限、当前帧缓存、精度、运算公式和 fallback 不变。新增检查覆盖空/稀疏/全区域、非连续/逆序数组、两种浮点精度、4095/4096 边界及非当前帧/非 uint8 fallback。

在 video_2 的 23 个固定输入上做四轮交替反序比较；双网络结果预计算一次，两个 Runtime 独立状态，各轮 12 次预热后重置。92 次比较的 S2/G0 掩膜逐像素一致，G0 几何和 S2 cap 在绝对容差 1e-9 内一致。输入哈希逐项匹配第八轮完整结果。

## 下一步实现顺序

1. **先建立独立实时测量壳。** 用 30 FPS 按时间到达的输入重放，记录采集/进入 NN/NN 完成/进入后处理/结果/实际呈现时刻及 frame_id。原始当前画面与可用的成对叠加画面分开处理；过期结果不冒充当前。先验证帧号与时间戳、更新间隔、超时比例、有效结果 Hz，再连接实际内镜测设备缓冲和显示。后台录像/诊断导出不阻塞实时路径，其代价仍需记录。
2. **先把 CPU 主路径压向 30 ms，并优化尾部。** 优先研究 QualifiedSeedObserver 的重复组件标签与 isolated mask 构建、相同组件坐标复用、相同几何上下文的 profile/采样索引共享及生长区域重复扫描。保留完整连通传播、阈值、迭代次数和像素坐标，不使用缩短迭代、跳过失败帧或截断连通域来制造提速。本轮区域索引只有亚毫秒局部空间，不再把它作为主要突破口。
3. **同步检查网络尾部。** 当前完整网络服务 P95 已超过 30 ms，不能因网络均值低于 33.33 ms 就忽略。先按帧关联前处理、传输、CUDA forward 和 CPU 调度，定位尾部来自哪里。仍使用 FP32、batch=1、原模型；不要优先扩大 batch 或积累多帧，不重启自定义 DLL。
4. **调度和状态作为独立行为实验。** 最新采集槽、最新就绪结果槽可作为过载防积压候选，但必须按实际选中的序列重放，比较相同序列的调度/参考实现；另评估跳帧相对完整运行的覆盖、遮挡恢复和时间有效期，不能要求或宣称天然逐像素相同。若选择逾期不叠加，必须公开有效分割缺失率，而非宣布延迟问题已经解决。
5. **最后验收真实采集到呈现。** 冷启动单列，稳态包含快速运动、遮挡、无目标、强反光等已有材料及实际连续输入；给出延迟尾部、最大值、超时和缺失、最长无更新时间及资源增长。没有实际采集/显示链路，本轮无法给出 100 ms 达标结论。
